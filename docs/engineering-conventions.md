# Engineering conventions

Updated on 2026-10-13 after the user selected Java and Spring Boot for the
backend. Use these rules for new implementation and review. The Java backend
at `apps/backend` implements the first foundation slice. Frontend and shared
TypeScript helpers remain planned.
The Python/Django scaffold and reporting prototype were removed at the user's
request on 2026-10-13. Reporting requirements remain in
[the reporting contract](reporting-contract.md); Java reporting is pending.

## Selected patterns

| Area | Choice | Purpose |
| --- | --- | --- |
| Overall system | Modular monolith packaged by feature | One Spring Boot backend and database, with modules organized around workflows |
| Backend writes | Application service layer | One authorized, validated path for a business operation |
| Backend reads | Authorized query services | Keep household-scoped reads out of controllers and pure calculations |
| Persistence | Spring Data JPA repositories | Encapsulate entity queries and persistence within their feature |
| Financial logic | Pure functions with explicit inputs | Reproduce totals and test rules without HTTP, database, or AI dependencies |
| External integrations | Ports and adapters at the boundary | Swap an extraction provider or storage implementation behind a small interface |
| Frontend | Feature modules and component composition | Keep a workflow's UI, API calls, and state together |
| Common functions | Small modules with named exports | Share stable date, money, and error behavior across web and future mobile |

Use Spring's constructor injection and Spring Data's repository interfaces.
Organize by feature, then by responsibility inside that feature. Keep service
interfaces for actual substitution/module contracts, not automatically for every
class. Introduce abstractions for concrete integration needs; the current
workflows fit one backend and database.

## Backend responsibilities

```text
HTTP controller -> validated request DTO -> application service -> repository -> PostgreSQL
HTTP controller -> authorized query service -> scoped repository -> pure report -> response DTO
Java worker/CLI -> application service -> provider/storage adapter
```

- **Controllers** handle HTTP, authenticated identity, DTO mapping and status.
  They delegate ledger operations to services and never call repositories directly.
- **DTOs** are request/response records, separate from entities. Use Jakarta Bean
  Validation for input shape/ranges and explicit field names for the JSON contract.
  HTTP validation alone is insufficient for workers, CLIs and future MCP callers.
- **Application services** expose operations such as `createAccount`,
  `confirmStatement` and `removeMember`. Accept an explicit actor and household
  scope; authorize current membership/role and validate every related object.
  Own transactions and locks for multi-record changes.
- **Query services** authorize reads, execute scoped repository queries and
  return DTOs/projections. For example, `findByIdAndHouseholdId` prevents reading
  an object from another scope; the ID still never grants membership by itself.
- **Repositories** belong to their feature and handle persistence. Avoid exposing
  unrestricted lookup methods to controllers/adapters or using Spring Data REST
  to bypass application authorization with autogenerated entity APIs.
- **Domain calculations** operate on immutable values without JPA, HTTP, clocks
  or provider calls. Use [the reporting contract](reporting-contract.md) and
  synthetic acceptance cases to verify the future Java reporting implementation.
- **Adapters** translate external formats/responses behind a Java interface
  such as `StatementExtractor`. Use fake implementations for offline experiments;
  keep provider SDK objects and transport errors inside the adapter.

Package structure: identity, households, accounts, and shared are implemented;
the diagram below is the target layout. AccountController/API packages and
other feature packages are added when their workflows are built.

```text
apps/backend/src/main/java/com/expensetracker/
  ExpenseTrackerApplication.java
  identity/
  households/
  accounts/
    api/                 AccountController, request/response DTOs
    application/         AccountService, AccountQueryService
    domain/              Account and domain rules
    persistence/         AccountRepository
  statements/            Private metadata, source access, staged review
  transactions/          Confirmed ledger and export
  categories/            Categories and later explicit rules
  reports/               Scoped reporting queries and pure calculations
  imports/               Extraction orchestration and provider adapters
  shared/                Small error/configuration/value modules

apps/backend/src/main/resources/db/migration/   Flyway SQL migrations
apps/backend/src/test/                         Unit and PostgreSQL integration tests
```

The application class sits above feature packages so component/entity scanning
covers them. A feature uses another feature through an explicit application
contract rather than its internal repository. Keep `shared` small and named;
do not move every helper or business rule there. [Spring Boot code structure](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html).

Use service-level `@Transactional` for writes and read-only transactions where
appropriate for queries. Calls must pass through Spring-managed proxies;
self-invocation can bypass transactional interception. Define rollback behavior
for any checked exceptions introduced. A read-only transaction is a performance
hint, not a permission check. [Spring Data transactions](https://docs.spring.io/spring-data/jpa/reference/jpa/transactions.html),
[Spring transaction annotations](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html).

For an existing household, shared mutations first acquire its pessimistic write
lock, then check current membership and object scope. Membership changes,
confirmation, deletion and worker writes use the same protocol and lock order.
Use database constraints in addition to service validation. Avoid entity mutation
outside write services and bulk writes that bypass those checks. Disable Open
EntityManager in View (`spring.jpa.open-in-view=false`); fetch and map required
fields within the service transaction.

Flyway owns schema changes; Hibernate uses `ddl-auto=validate`. Verify migrations,
constraints, races and rollback against PostgreSQL, using Testcontainers with
a supported container runtime. H2/SQLite checks do not verify PostgreSQL behavior.
[Spring Boot database initialization](https://docs.spring.io/spring-boot/how-to/data-initialization.html),
[Spring Boot Testcontainers](https://docs.spring.io/spring-boot/reference/testing/testcontainers.html).

Java workers reuse backend services. Keep provider/network calls outside ledger
transactions. Durable external cleanup runs after commit from records that
survive household deletion. See [architecture](architecture.md) and
[backend transition](backend-transition.md).

## Next.js organization

Target layout; create files as their workflows are implemented:

```text
apps/web/src/
  app/                         Route pages, layouts, loading and error states
  features/
    accounts/
    imports/
      components/              Upload and source-aware review UI
      api/                     Import endpoints and DTO-to-view-model mapping
      hooks/                   Interactive workflow state when needed
      validation/              Form rules specific to import review
    transactions/
    reports/
  components/ui/               Web-wide buttons, dialogs, table primitives
  lib/api/                     HTTP transport, CSRF handling, error mapping
  lib/server/                  Session forwarding and server-only configuration
  lib/formatting-context.ts    Resolved locale and display time zone

packages/
  contracts/                   Generated API DTOs; no formatting or UI
  shared/src/
    dates.ts                   Validated date types and date formatters
    money.ts                   Minor-unit parsing and exact money formatting
    api-errors.ts              Common error value types and safe normalization
```

Routes compose features. A feature owns its business UI and may use shared
utilities or web UI primitives. Cross-feature reuse goes through a narrow,
explicit public entry point; do not import another feature's private hook or
component. Shared code must not import an application or feature.

Keep server and client exports separate. Mark sensitive web modules with
`server-only`; do not re-export them from a common barrel. Use Server Components
for initial rendering/data reads and Client Components where events, browser
APIs, or interactive state require them. Spring Boot remains responsible for ledger
mutations and authorization. These choices fit the App Router's supported
organization and component boundaries. [Next.js project structure](https://nextjs.org/docs/app/getting-started/project-structure),
[Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components).

Keep local UI state in components or feature hooks first. Introduce a server
data cache library when a real workflow needs it. Private API responses use
`Cache-Control: private, no-store` by default; authenticated Next.js data fetches
use `cache: 'no-store'`. If caching is later introduced, verify current
membership/role before every response, including a cache hit, and include the
relevant user/household scope in cache keys. Client data clearing on logout,
household switch, or membership loss is additional UI behavior, not access
control. Frontend role flags never authorize a backend operation.
[Next.js fetch caching](https://nextjs.org/docs/app/api-reference/functions/fetch).

## Where a shared function belongs

| Function or rule | Owner |
| --- | --- |
| Date-only, month, timestamp and money display | `packages/shared` |
| API DTO/schema | `packages/contracts`, generated from implemented API |
| Browser/server HTTP transport and cookies | `apps/web/src/lib`, with server-only parts isolated |
| Button, dialog, responsive table | `apps/web/src/components/ui` |
| Import-review form rule or hook | `apps/web/src/features/imports` |
| Issuer-specific date/amount normalization | Backend import adapter |
| Spending totals, refund treatment, confirmation rules | Backend services/pure reporting functions |
| Household access, related-object checks, deletion | Backend application/query services |

Share functions when multiple callers need the same meaning and behavior. Keep
feature-specific helpers local. Use named modules such as `dates.ts` and
`money.ts` instead of a growing `utils.ts` or one general `formatDate` function.
The shared package is pure TypeScript: no React, Next.js, DOM globals, secrets,
environment access, HTTP calls, or model-provider SDKs.

Java and TypeScript do not share one implementation directly. Keep financial
rules authoritative in Java; share API schemas and synthetic examples across
languages. The first offline extraction/evaluation runner also uses Java. Later
training or serving experiments may choose separately scoped tooling as needed.
Do not recreate the spending engine in the UI.

## Date contract and formatter names

| Value | API format | Display policy |
| --- | --- | --- |
| Posted/purchase date, statement period date | `YYYY-MM-DD`, e.g. `2026-10-13` | Calendar date; never shift with the viewer's time zone |
| Report month | `YYYY-MM`, e.g. `2026-10` | Calendar month; not a timestamp |
| Event instant, e.g. job creation | UTC ISO timestamp with `Z`, e.g. `2026-10-13T18:30:00Z` | Convert to an explicitly selected display time zone |

Java uses `LocalDate` for calendar dates, `YearMonth` for reporting months, and
`Instant` for event timestamps. Serialize explicitly to the formats above;
never turn a posted date into a midnight instant to persist or transport it.

Validate the actual calendar date, including leap years, at the API boundary
and in shared parsers; a matching regular expression is insufficient. Keep
date-only and instant values distinct in types and functions. Issuer adapters
may accept raw source text, but normalized API values follow this contract.

Planned shared API:

```typescript
parseDateOnly(value: unknown): DateOnly;
parseMonthKey(value: unknown): MonthKey;
parseUtcInstant(value: unknown): UtcInstant;
formatPostedDate(value: DateOnly, options: { locale: string }): string;
formatMonth(value: MonthKey, options: { locale: string }): string;
formatTimestamp(value: UtcInstant, options: {
  locale: string;
  timeZone: string;
}): string;
```

These signatures are a design contract, not implemented exports. Branded string
types are produced by runtime parsers; a TypeScript cast is not validation.
Use `Intl.DateTimeFormat` for display. For date-only/month formatting, parse
calendar components and format in UTC deliberately so `2026-10-13` stays
October 13 everywhere. Do not pass a date-only value through the viewer's local
timestamp formatter: JavaScript interprets ISO date-only strings as UTC, which
can display the previous day in a western time zone. [Date.parse](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Date/parse),
[Intl.DateTimeFormat](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat).

Resolve locale and display time zone centrally from explicit settings/defaults,
then pass the same values to server and client rendering. Do not rely on the
server's OS locale, browser defaults, or implicit local time. Calendar ranges
and coverage remain backend decisions. Add a date arithmetic library only when
a concrete requirement exceeds these display helpers.

## Money contract and formatter

Store positive integer minor units in Java `long`/PostgreSQL `BIGINT`. Accumulate
report totals and deltas with `BigInteger`; use checked operations such as
`Math.addExact` for bounded `long` arithmetic. Never narrow an aggregate silently
or use `double`/`float` for money. [Java Math exact arithmetic](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Math.html).

On the normalized
ledger/report JSON boundary, every minor-unit amount, total, and delta is a
**canonical decimal integer string**, with an explicit currency:

```json
{"amount_minor": "1250", "currency": "USD"}
```

This is $12.50. It is not the decimal dollar string `"12.50"`. Transaction
amounts are positive; report net totals/deltas may be signed or zero. For
example, a one-cent decrease is `"-1"`. An unresolved staged amount can be
`null`; preserved `raw_amount_text` keeps the source's original representation.

API DTO parsing must reject numeric JSON inputs, floats, exponents, whitespace,
group separators, leading zeroes, plus signs, and negative zero. Bound input
length and enforce the field's database/domain range. Report aggregates use
their own documented bounds, not an individual transaction's range. OpenAPI
describes these fields as strings with appropriate patterns/nullability, so
generated TypeScript DTOs retain strings.

Require an actual JSON string token before parsing money; Jackson's ordinary
string coercion must not silently accept numeric JSON. Request format validation
and domain range checks both apply when internal callers bypass HTTP.

Inside a formatter, validate and parse to `bigint` without going through
`Number`. Keep transport DTOs as strings; explicitly use `.toString()` when
serializing any internal `bigint`. JavaScript numbers cannot exactly represent
all database-sized integers or large sums. [Number.MAX_SAFE_INTEGER](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/MAX_SAFE_INTEGER).

Planned helpers:

```typescript
parseMinorUnits(value: unknown): MinorUnits; // validated canonical string
formatMoney(value: MinorUnits, currency: SupportedCurrency,
  options: { locale: string }): string;
```

Start with USD and exponent 2. Reject unsupported currencies until their
exponents and tests exist. Formatting uses exact integer/string conversion
and `Intl.NumberFormat`; never implement it as `Number(value) / 100`. Verify
exact decimal-string formatting on supported browser/mobile runtimes before
depending on that capability. [Intl.NumberFormat.format](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat/format).

Compare amounts numerically, not by string sorting. A chart may convert to a
bounded approximation for plotting only; exact labels and all report facts use
the original values. Invalid/missing amounts display a review/error state,
never a silent zero. Currency conversion, financial totals, and rounding rules
remain in the backend.

## Errors, checks, and adoption

Use stable backend error codes and field errors; map them to readable messages
at the frontend boundary. Do not parse human-readable error text for logic or
show raw provider exceptions. Client form checks improve feedback; the backend
repeats all authoritative validation and authorization.

Add meaningful checks with implementation:

- Shared formatters: leap day and invalid dates; date-only unchanged in Chicago
  and Tokyo; timestamp time-zone conversion; identical server/client settings.
- Money: USD zero, positive and negative amounts, `"-1"` -> `-$0.01` in
  `en-US`, an amount above JavaScript's safe integer limit, invalid text,
  unsupported currency, and unresolved staged values.
- Services/query services: allowed household access, revoked/nonmember denial,
  foreign-object substitution, atomic confirmation, and last-owner races.
- API contracts: exact string round-trips for amounts/totals/deltas; runtime
  rejection of malformed inputs; regenerate types from real endpoints.
- Frontend workflow: source review, field-error feedback, repeated confirmation,
  and household changes without stale private data.

The next implementation is [Phase 0B session and account API](next-move.md), on
the existing Phase 0A.1 services. Implement shared formatters and their
checks when the first Next.js workflow is introduced; configure strict
TypeScript, lint import boundaries, and generate contracts as APIs become real.
Do not create empty classes or placeholder layers to satisfy the pattern names.
